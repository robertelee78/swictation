# ADR-028: Fix postinstall CoreML Model Sequencing and Platform-Aware Test Configuration

**Status:** Accepted
**Date:** 2026-03-24
**Authors:** Robert (Product Owner), Winston (Architect), Quinn (QA), John (PM), Amelia (Dev), Mary (Analyst)
**Deciders:** Robert
**Scope:** postinstall.js install flow, daemon config parsing, daemon dry-run verification
**Resolves:** GitHub Issue #3

---

## Context

On a fresh macOS Apple Silicon install of swictation v0.7.30, the postinstall script always falls back to `cpu-only` mode instead of using CoreML/ANE-accelerated inference. Every fresh macOS install is affected -- users get significantly degraded performance and the wrong model downloaded.

A comprehensive code audit revealed this is not a single bug but a cluster of 10 interrelated issues spanning the postinstall script, daemon config parsing, and daemon dry-run verification. The root cause is a chicken-and-egg sequencing bug compounded by missing platform awareness in the test infrastructure.

### How the Bug Manifests

```
Fresh macOS Apple Silicon install:

1. detectUnifiedMemoryMacOS()      -> recommendedModel = '1.1b-coreml'     OK
2. downloadONNXRuntimeCoreML()     -> downloads runtime .dylib              OK
3. testModelsInOrder()             -> dry-runs daemon with 1.1b-coreml      FAIL
   |-- Config missing stt_coreml_model_path -> daemon can't parse config
   |-- Model files not downloaded yet -> even if config parsed, nothing on disk
   |-- timeout command not on stock macOS -> exec fails before daemon runs
4. gpu-info.json overwritten       -> recommendedModel = 'cpu-only'
5. showNextSteps()                 -> downloads 0.6b ONNX (CPU) model       WRONG
```

The model download (`autoDownloadModel`) is called inside `showNextSteps()` at line 3095, which is 80 lines **after** the model test at line 3015. On a fresh install the CoreML model directory does not exist, so the test fails and the recommendation is downgraded to `cpu-only`.

### Scope of Impact

- **100% of fresh macOS Apple Silicon installs** on v0.7.30 hit this bug
- Users get CPU-only mode instead of CoreML/ANE acceleration
- Wrong model downloaded (0.6b ONNX instead of 1.1b CoreML)
- `gpu-info.json` persists `"recommendedModel": "cpu-only"` despite capable hardware
- The same sequencing bug also affects Linux (model test before model download)

---

## Decision

Fix all 10 identified issues in a single commit/PR. The issues are tightly coupled -- fixing only the sequencing without fixing the config template would still leave the test broken, and vice versa.

## Changes

### Item 1: Move model download before model test (both platforms)

**File:** `npm-package/postinstall.js` -- `main()`, after line 3012 (before line 3014)

**Problem:** `autoDownloadModel()` is called in `showNextSteps()` (line 2821), but `testModelsInOrder()` runs at line 3015 -- 80 lines earlier. On fresh installs on both macOS and Linux, the model test always fails because the model files don't exist yet.

**Solution:** Insert a platform-agnostic `autoDownloadModel(gpuInfo.recommendedModel)` call between the platform detection block and the model test block. `autoDownloadModel()` already guards against re-download via `isModelDownloaded()`. If the download fails (network error, disk full), skip the model test and preserve the memory-based heuristic recommendation.

**Why not just move the test after showNextSteps?** The test results are used to update `gpu-info.json` (lines 3024-3038) and generate service configs (lines 3044-3049). These must happen before `showNextSteps()`.

### Item 2: Add `stt_coreml_model_path` to temp config

**File:** `npm-package/postinstall.js` -- `testLoadModel()`, lines 2114-2146

**Problem:** The temp `config.toml` generated by `testLoadModel()` is missing the `stt_coreml_model_path` field. `DaemonConfig` in Rust has no `#[serde(default)]` on this field, so `toml::from_str()` fails with a deserialization error. The daemon can't even start, let alone reach the dry-run path.

**Solution:** Add `stt_coreml_model_path = "${modelDir}/parakeet-tdt-1.1b-coreml"` to the temp config template. This matches the daemon's compiled default at `config.rs:37-38`.

**Note:** This "temp" config persists as the user's permanent `~/.config/swictation/config.toml` -- `testLoadModel()` never cleans it up, and the daemon loads it on subsequent starts instead of generating its own defaults. All fields must be complete and correct.

### Item 3: Fix `stt_0_6b_model_path` directory name in temp config

**File:** `npm-package/postinstall.js` -- `testLoadModel()`, line 2130

**Problem:** The temp config uses `sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-onnx` (the HuggingFace repo name) instead of `parakeet-tdt-0.6b-v3-onnx` (the actual download target directory). The daemon default (`config.rs:22`) and model-downloader (`model-downloader.js:40`) both use `parakeet-tdt-0.6b-v3-onnx`. If the daemon ever fell back to the 0.6b model on Linux, it would look in the wrong directory.

**Solution:** Change line 2130 to use `parakeet-tdt-0.6b-v3-onnx`.

### Item 4: Platform-branch environment variables in `testLoadModel()`

**File:** `npm-package/postinstall.js` -- `testLoadModel()`, lines 2154-2166

**Problem:** The test unconditionally sets Linux-specific environment variables on macOS:
- `detectCudaLibraryPaths()` scans `/usr/local/cuda/*` -- doesn't exist on macOS
- `LD_LIBRARY_PATH` -- Linux-only, macOS uses `DYLD_LIBRARY_PATH`
- `CUDA_HOME = '/usr/local/cuda'` -- Linux-only

Meanwhile, the macOS production environment (launchd plist wrapper) uses `DYLD_LIBRARY_PATH` and `ORT_DYLIB_PATH`. However, investigation of `libonnxruntime.dylib` via `otool -L` confirmed all its dependencies are system frameworks at absolute paths. `DYLD_LIBRARY_PATH` is not needed when `ORT_DYLIB_PATH` is an absolute path (which it is). The `ort` crate (`lib.rs:82`) reads `ORT_DYLIB_PATH` directly and passes it to `libloading::Library::new()` at the absolute path.

Additionally, the daemon dry-run path (`main.rs:427-471`) never initializes the ORT environment -- ORT is only loaded inside `Pipeline::new()` which runs after the dry-run early return. So technically `ORT_DYLIB_PATH` is also not required for dry-run. We set it defensively for forward compatibility.

**Solution:**
- macOS: Set `ORT_DYLIB_PATH` (defensive, matches production) and `RUST_LOG=info`. No `LD_LIBRARY_PATH`, no `CUDA_HOME`, no CUDA path detection.
- Linux: Keep existing `ORT_DYLIB_PATH`, `LD_LIBRARY_PATH`, `CUDA_HOME`, CUDA path detection, `RUST_LOG=info`.

### Item 5: Replace shell `timeout` with Node.js `execSync` timeout

**File:** `npm-package/postinstall.js` -- `testLoadModel()`, line 2169

**Problem:** The command uses `timeout 30s "${daemonBin}"` -- `timeout` is a GNU coreutils utility not shipped with macOS. On a fresh Mac without Homebrew, `execSync` fails with "command not found" before the daemon even runs.

**Solution:** Remove shell `timeout` from the command string. Use Node's native `execSync({ timeout: 30000 })` option instead. This works identically on both platforms with no external dependencies.

### Item 6: Fix hotkey defaults in temp config and remove push-to-talk

**File:** `npm-package/postinstall.js` -- `testLoadModel()`, lines 2141-2145; `npm-package/docs/MACOS_SETUP.md`

**Problem:** The temp config always writes Linux hotkeys regardless of platform:
```toml
toggle = "Super+Shift+D"     # Wrong on macOS (this is Command+Shift+D)
push_to_talk = "Super+Space"  # Feature not supported
```

The daemon's compiled defaults (`config.rs:58-61`) correctly use `Ctrl+Shift+D` on macOS (physical Control key, via `global-hotkey` crate's `Modifiers::CONTROL` -> Carbon `controlKey` 4096) and `Super+Shift+D` on Linux. Push-to-talk is not a supported feature.

Additionally, `MACOS_SETUP.md` documents the hotkey as "Cmd+Shift+D" which is incorrect -- the actual macOS hotkey is Ctrl+Shift+D.

**Solution:**
- Platform-branch the temp config hotkey section: macOS uses `Ctrl+Shift+D`, Linux uses `Super+Shift+D`
- Remove `push_to_talk` from the temp config entirely (daemon falls back to its compiled default -- existing behavior, separate cleanup concern)
- Fix `MACOS_SETUP.md` to document `Ctrl+Shift+D`

### Item 7: Fix `isModelDownloaded()` directory name mappings

**File:** `npm-package/postinstall.js` -- `isModelDownloaded()`, lines 2650-2655

**Problem:** The function maps model names to HuggingFace repo names instead of actual download target directories:

| Model | Current (wrong) | Correct (matches model-downloader targetDir) |
|---|---|---|
| `'0.6b'` / `'0.6b-gpu'` | `sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-onnx` | `parakeet-tdt-0.6b-v3-onnx` |
| `'1.1b'` / `'1.1b-gpu'` | `sherpa-onnx-nemo-parakeet-tdt-1.1b-v3-onnx` | `parakeet-tdt-1.1b-onnx` |
| `'cpu-only'` | `sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-onnx-int8` | `parakeet-tdt-0.6b-v3-onnx` |

This causes `isModelDownloaded()` to always return `false`, so `autoDownloadModel()` re-downloads on every install even if the model already exists.

**Solution:** Update the mappings to match `model-downloader.js` `targetDir` values. The `'cpu-only'` key maps to the same directory as `'0.6b'` since there is no separate INT8 download target.

**Verification:** Confirmed on-disk directory names via `ls ~/.local/share/swictation/models/` match the model-downloader `targetDir` values.

### Item 8: Add serde default for `stt_coreml_model_path` in daemon config

**File:** `rust-crates/swictation-daemon/src/config.rs`, line 115

**Problem:** `DaemonConfig` uses `#[derive(Deserialize)]` with no `#[serde(default)]` on the struct or the `stt_coreml_model_path` field. Any config.toml from before CoreML support was added -- or any hand-edited config that omits this field -- crashes the daemon on startup with a TOML parse error. This is a latent time bomb for upgrades.

**Solution:** Add `#[serde(default = "get_default_coreml_model_path")]` to the `stt_coreml_model_path` field. This makes the daemon resilient to configs missing this field while preserving the correct default path (`models/parakeet-tdt-1.1b-coreml`).

**Why not add `#[serde(default)]` to the whole struct?** The strict parsing on other fields is a safety net that catches typos and missing required fields. We only relax the constraint for the newly-added field that didn't exist in older configs. This is a surgical, intentional relaxation.

### Item 9: Add model file verification to daemon dry-run

**File:** `rust-crates/swictation-daemon/src/main.rs`, lines 427-471

**Problem:** The daemon's `--dry-run` mode just prints "Would load" and "Dry-run complete" without checking if model files actually exist on disk. The postinstall script checks for the string "Dry-run complete" as a success signal (`postinstall.js:2176`). This means a failed or partial download would still appear to pass the postinstall test.

**Solution:** Add primary model file existence checks in the dry-run match arms:
- `1.1b-coreml`: check `stt_coreml_model_path.join("encoder.mlmodelc").exists()`
- `1.1b-gpu`: check `stt_1_1b_model_path.join("encoder.int8.onnx").exists()`
- `0.6b-gpu` / `0.6b-cpu`: check `stt_0_6b_model_path.join("encoder.onnx").exists()`

If the primary model file exists, print "Dry-run complete" (exit 0). If missing, log an error and do NOT print "Dry-run complete" -- postinstall sees this as a failure. Also add the same checks to the `auto` mode branch.

**Why check only the primary file?** If the encoder exists, the download succeeded. Checking every file is overkill for a postinstall smoke test. The full model validation happens when the daemon starts for real.

### Item 10: Remove stale `detected-environment.json` from git tracking

**Files:** `.gitignore`, `npm-package/config/detected-environment.json`, `npm-package/package/config/detected-environment.json`

**Problem:** `detected-environment.json` contains a machine-specific Linux `.so` path from a November 2025 dev install. Investigation confirmed:
- **Writer:** `detectOrtLibrary()` at `postinstall.js:1170` -- only called on Linux, Priority 3 Python fallback path
- **Reader:** Nothing. Zero `readFileSync` or `require()` calls against this file anywhere in the codebase
- **Test reference:** `docker-advanced-test.sh:97` checks if it exists and `cat`s it for diagnostics, with a graceful "not found" fallback
- The file is never updated on macOS because `detectOrtLibrary()` is never called for darwin

The file is dead write-only state that got committed accidentally.

**Solution:** Add both paths to `.gitignore` and remove from git tracking with `git rm --cached`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Model download before test adds time to install | `autoDownloadModel()` already runs in `showNextSteps()` -- we're moving it earlier, not adding a new download. Same total time. |
| `isModelDownloaded()` directory name changes could break something | Verified on-disk names match model-downloader `targetDir` and daemon `config.rs` defaults. The old names never matched reality. |
| serde default on `stt_coreml_model_path` changes daemon config behavior | Only relaxes constraint for one field, and only when missing. Existing configs with the field present are unaffected. |
| Dry-run model verification could cause false negatives | Only checks primary encoder file (smoke test). If encoder exists, download succeeded. Full validation happens at daemon startup. |
| Removing `detected-environment.json` from git | Nothing reads this file. Docker test handles its absence gracefully. |

## Alternatives Considered

### Skip the model test entirely on macOS
Rejected. The test serves a real purpose (verifying daemon binary can start and parse config). Fixing it is better than removing it.

### Add `#[serde(default)]` to the entire `DaemonConfig` struct
Rejected. Strict parsing catches typos and missing required fields. We only relax the constraint for the newly-added CoreML field that didn't exist in older configs.

### Make the dry-run actually load models
Rejected. Loading models takes significant time and memory. A file-existence check is sufficient for postinstall verification. Full model loading happens at daemon startup.

### Fix only the sequencing bug (Issue #3 as filed)
Rejected. The sequencing fix alone would not resolve the problem because the temp config is also missing `stt_coreml_model_path`. Both issues must be fixed together, and the remaining 8 issues are in the same code paths with the same blast radius.

## Implementation Principles

This fix adheres to our core engineering mantra:

> DO NOT BE LAZY. We have plenty of time to do it right. No shortcuts. Never make assumptions. Always dive deep and ensure you know the problem you're solving. Make use of search as needed. Measure 3x, cut once. No fallback. No stub (todo later) code. Just pure excellence, done the right way the entire time. Also recall Chesterton's fence; always understand current fully before changing it.

Every item in this ADR was validated by reading the actual code paths end to end -- daemon Rust source, postinstall JavaScript, ort crate internals, global-hotkey crate Carbon bindings, and on-disk model directory names. No changes were proposed based on assumptions. Each "Why" was confirmed by tracing execution, and each "What" was validated against production behavior before being accepted.

## Acceptance Criteria

1. Fresh `npm install -g swictation` on macOS Apple Silicon produces `gpu-info.json` with `"recommendedModel": "1.1b-coreml"`
2. CoreML model directory (`parakeet-tdt-1.1b-coreml`) is downloaded and contains `encoder.mlmodelc`, `decoder.mlmodelc`, `joiner.mlmodelc`, `tokens.txt`
3. Daemon dry-run passes with "Dry-run complete" in output
4. No `timeout` command dependency on macOS
5. Postinstall log shows no "failed to load" errors for CoreML model
6. `~/.config/swictation/config.toml` contains `stt_coreml_model_path` with correct path
7. `isModelDownloaded('1.1b-coreml')` returns `true` after download
8. Re-running install does not re-download existing models
9. Linux install flow continues to work correctly with NVIDIA GPU detection
10. Existing config.toml files missing `stt_coreml_model_path` don't crash the daemon
